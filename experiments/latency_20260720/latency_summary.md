## 2. 측정 방법

### 2.1 시계 동기화 문제와 2트랙 설계

두 기기의 시스템 클럭 오차가 측정 대상(수 ms~수십 ms)과 같은 크기이므로, 두 기기에
걸친 단순 편도 측정은 신뢰할 수 없다. 따라서 다음 2트랙으로 분리했다.

- **트랙 A (단일 기기, 프로세스 분리):** sender/receiver를 같은 PC에서 별개 프로세스로
  실행. 클럭이 동일하므로 각 구간 편도 지연을 정확히 분해할 수 있다. 단 무선 구간이
  포함되지 않는다.
- **트랙 B (2기기, 에코백 RTT):** 수신측이 수신 즉시 ACK를 회신하고, 송신측이
  송신시각과 ACK 수신시각을 **같은 클럭으로** 측정 → RTT. 시계 동기화가 불필요하다.

### 2.2 계측 지점

`event_id`(uuid4 12자리)로 두 CSV를 조인한다.

| 단계 | 기록 위치 | 의미 |
|---|---|---|
| `frame_capture` | sender | 프레임 디코드 완료 시각 |
| `yolo_detect_done` | sender | YOLO 추론 반환 시각 |
| `udp_send` | sender | `sendto()` 반환 시각 |
| `udp_receive` | receiver | `recvfrom()` 반환 시각 |
| `ui_alert_shown` | receiver | `pygame.display.flip()` 직후 |
| `ack_recv` | sender | (트랙 B) ACK 수신 시각 |

### 2.3 워밍업

첫 추론은 모델 로딩·메모리 할당 때문에 항상 느리므로 **워밍업 30 이벤트**를 먼저
돌린 뒤 본 측정을 시작했다. 워밍업 데이터는 **통계에서 제외**하되 raw CSV에는
`extra` 필드에 `warmup` 태그가 붙은 채 그대로 남아 있다.

### 2.4 실행 명령 (재현용)

```powershell
# 수신측 (별도 프로세스)
python receiver.py --csv experiments\latency_20260720\raw\trackA_receiver.csv --exit-after 230

# 송신측
python sender.py --input assets\mixkit_highway_pov_42364.mp4 `
                 --target 192.168.0.15 --max-events 200 --warmup 30 `
                 --force-emit --csv experiments\latency_20260720\raw\trackA_sender.csv

# 분석
python analyze_latency.py --sender raw\trackA_sender.csv `
                          --receiver raw\trackA_receiver.csv `
                          --outdir . --label trackA --hist
```

### 2.5 측정 조건상의 한계 (반드시 함께 인용할 것)

1. **영상 파일 재생은 실제 카메라 캡처 지연을 포함하지 않는다.** 본 측정의
   `frame_capture`는 파일 디코드 완료 시점이며, 실제 카메라의 노출·전송·드라이버
   지연은 빠져 있다. 실환경 종단간 지연은 여기에 카메라 캡처 지연이 더해진다.
2. **프레임을 실시간 속도로 재생하지 않았다.** 재생속도가 병목이 되지 않도록 최대
   속도로 처리했다(230프레임 18.7초, 약 12.3 FPS = 추론 자체의 처리율). 따라서 본
   수치는 파이프라인의 순수 처리 지연이다.
3. **`--force-emit` 모드를 사용했다.** 위험 미검출 프레임에서도 패킷을 송신해
   표본 수를 확보했다. 이 모드는 **지연시간 측정 전용**이며 **위험 판단 정확도와는
   무관**하다. 이 데이터를 탐지 성능 근거로 인용해서는 안 된다.
4. 트랙 A의 "네트워크 편도"는 **동일 기기 내 WiFi 인터페이스 경유** 값이므로 실제
   무선 구간 지연이 아니다. 실제 무선 지연은 트랙 B로 별도 측정한다.

## 4. 트랙 B 결과 — 무선 구간 RTT

> **상태: 측정 완료 (2026-07-20 22:56)**

### 4.0 측정 결과

**표본 200회 (워밍업 30 제외), 패킷 유실 0건**

| 지표 | 평균 | 중앙값 | p95 | p99 | 최대 | 최소 | 표준편차 |
|---|---|---|---|---|---|---|---|
| **RTT (udp_send→ack_recv)** | **24.50** | **13.09** | **62.61** | 239.48 | 314.54 | 5.47 | 37.86 |
| 편도 추정 (RTT/2) | 12.25 | 6.54 | 31.31 | 119.74 | 157.27 | 2.74 | — |

*(단위 ms)*

**왕복 패킷 유실률 0.0 %** (송신 200건 / ACK 수신 200건). 참고로 워밍업 30건 중
5건은 ACK가 오지 않았는데, 이는 폰의 WiFi 절전 상태에서 깨어나는 초기 구간이다.
워밍업을 통계에서 제외한 설계가 정확히 이 구간을 걸러냈다.

### 4.0.1 분포 해석 — 평균보다 중앙값을 쓸 것

**평균(24.50)이 중앙값(13.09)의 약 1.9배**이고 p99가 239 ms, 최대가 314 ms다.
분포가 오른쪽으로 심하게 치우쳐 있다. 원인은 **안드로이드 WiFi 절전(power save)**로,
측정 전 `ping` 응답도 478 / 37 / 140 / 86 ms로 같은 패턴을 보였다(첫 패킷이 가장 느림).

따라서 대표값으로는 **중앙값 13.09 ms**가 적절하고, 보수적 상한으로는 **p95 62.61 ms**를
쓴다. 평균은 소수의 절전 복귀 지연에 끌려간 값이므로 단독 인용을 피한다.

편도는 RTT/2로 추정하되, **제안서 본문에는 보수적으로 RTT 기준으로 서술한다.**
RTT/2는 상·하향 경로가 대칭이라는 가정에 의존하는 추정치이며, WiFi는 실제로
비대칭일 수 있기 때문이다.

## 5. 종단간 지연 계산식

```
종단간 예상 지연 = 웹캠 캡처 지연        (보조측정, 미측정)
                + YOLO 추론 지연        (트랙 A)
                + 직렬화/송신 지연      (트랙 A)
                + 무선 편도 지연        (트랙 B RTT/2 — 추정치)
                + 수신/UI 표시 지연     (트랙 A)
```

### 5.1 각 항의 실측값

| 항 | 출처 | 평균 | 중앙값 | p95 |
|---|---|---|---|---|
| 웹캠 캡처 지연 | 보조측정 | *미측정* | *미측정* | *미측정* |
| YOLO 추론 지연 | 트랙 A | 73.04 | 72.58 | 81.60 |
| 직렬화/송신 지연 | 트랙 A | 1.81 | 1.80 | 2.20 |
| **무선 편도 (RTT/2)** | **트랙 B** | **12.25** | **6.54** | **31.31** |
| 수신/UI 표시 지연 | 트랙 A | 19.78 | 19.04 | 26.48 |

*(단위 ms. 트랙 A의 "네트워크 편도 0.78 ms"는 동일 기기 내 값이므로 종단간
계산에서 제외하고, 그 자리에 트랙 B의 무선 편도를 넣는다.)*

### 5.2 종단간 3기준

트랙 A 실측 종단간(95.40 평균 / 108.21 p95)에서 **동일기기 네트워크 구간을 빼고
트랙 B 무선 구간을 더한** 값이다.

| 기준 | 계산 | 종단간 |
|---|---|---|
| **① 대표(중앙값) 기준** | 94.95 − 0.68 + 6.54 | **100.81 ms** |
| **② 평균 기준** | 95.40 − 0.78 + 12.25 | **106.87 ms** |
| **③ 보수(p95 + RTT 전체) 기준** | 108.21 − 2.00 + 62.61 | **168.82 ms** |

**③이 가장 보수적**이다. p95 종단간에 **편도가 아닌 RTT 전체(62.61 ms)**를 그대로
더했다. RTT/2 추정이 상·하향 대칭을 가정하는데 WiFi는 비대칭일 수 있으므로,
제안서에서 안전하게 주장하려면 이 값을 쓴다.

> **⚠️ 과대추정 주의 (반드시 함께 인용할 것)**
>
> ③의 168.82 ms는 **서로 다른 구간의 p95를 합산**한 값이다. 실제 합의 p95는 이보다
> 작다 — 각 구간의 최악값이 동시에 발생할 확률은 매우 낮기 때문이다. 즉 ③은
> **실측된 상한이 아니라 계산상의 안전 상한**이다.
>
> 반대로 ①·②는 구간별 대표값을 더한 것이므로 **분포의 꼬리를 반영하지 않는다.**
> 어느 기준을 쓰든 단일 숫자로 "이 시스템의 지연"을 단정하지 말고, **기준을 명시해서**
> 서술할 것.
>
> 종단간 전체를 하나의 이벤트로 직접 측정한 값은 **트랙 A 구간(카메라·무선 제외)의
> 95.40 / 108.21 ms 뿐**이다. 무선을 포함한 종단간은 위 3기준 모두 **합성값**이다.

## 6. 200 ms 목표선 대비

| 기준 | 종단간 | 목표 200 ms 대비 | 여유 |
|---|---|---|---|
| ① 대표(중앙값) | **100.81 ms** | 50.4 % | 99.19 ms |
| ② 평균 | **106.87 ms** | 53.4 % | 93.13 ms |
| ③ 보수(p95+RTT) | **168.82 ms** | **84.4 %** | **31.18 ms** |
| (참고) 트랙 A 실측 p95 | 108.21 ms | 54.1 % | 91.79 ms |

**해석:** 세 기준 모두 200 ms 목표선 안에 들어온다. 가장 보수적인 ③에서도
**31.18 ms의 여유**가 남는다.

다만 ③의 여유는 얇다. 여기에 **아직 측정하지 않은 카메라 캡처 지연**이 더해지면
목표선을 넘을 수 있다. 일반적인 USB 웹캠 캡처 지연이 30~60 ms 수준임을 감안하면,
**③ 기준에서는 목표 달성을 단정할 수 없다.** 제안서에는 ①·② 기준으로 서술하되
③을 함께 제시해 한계를 드러내는 편이 방어적으로 안전하다.

### 6.1 이 수치의 한계 (제안서에 반드시 병기)

1. **카메라 캡처 지연 미포함** — 모든 기준에 공통. 실환경에서는 여기에 카메라
   노출·전송·드라이버 지연이 더해진다.
2. **영상 파일 입력** — 실시간 카메라가 아니라 파일 디코드 시점을 시작점으로 잡았다.
3. **무선 구간은 추정** — RTT/2는 경로 대칭 가정에 의존한다. ③은 이 가정을 피하려고
   RTT 전체를 썼다.
4. **단일 AP·단일 기기 쌍·1회 측정** — 다른 AP, 혼잡 환경, 차량 이동 중(도플러·핸드오버)
   조건은 측정하지 않았다. 실주행 무선 성능은 이보다 나쁠 가능성이 높다.
5. **CPU 부하 조건** — 트랙 A·B 모두 다른 무거운 작업이 없는 상태에서 측정했다.
   실제 차량 단말에서 다른 연산이 동시에 돌면 추론 지연이 늘어난다. 실제로 트랙 B
   실행 중 측정된 YOLO 추론은 84.88 ms 평균 / 123.34 ms p95로, 트랙 A(73.04 / 81.60)보다
   높았다 — 동일 기기라도 배경 부하에 따라 **추론 지연이 15~50 % 변동**한다.

## 7. 지배적 병목과 개선 방향

### 7.1 병목: YOLO 추론 (종단간의 76.6 %)

네트워크 전송(2.59 ms, 2.7 %)은 병목이 아니다. **병목은 온디바이스 YOLOv8n CPU 추론**
이며, 이미 nano 모델을 쓰고 있음에도 73 ms가 소요된다.

### 7.2 경량화 여지

입력 해상도를 imgsz 640 → 416/320으로 낮추면 연산량이 대략 해상도 제곱에 비례해
줄어 추론 시간을 절반 이하로 단축할 수 있고, INT8 양자화(OpenVINO·ONNX Runtime)를
적용하면 본 Intel CPU에서 추가로 2~3배 가속이 가능하다. 양산 단계에서는 차량용
NPU 델리게이트(예: TFLite NNAPI, OpenVINO GPU/NPU 플러그인)로 오프로딩해 CPU 부하를
제거하는 것이 근본적인 해법이다.

### 7.3 부차적 개선

UI 표시 지연 19.78 ms 중 상당 부분은 60 FPS 렌더 루프의 프레임 대기(최대 16.7 ms)다.
경고 발생 시 즉시 렌더를 트리거하는 방식으로 평균 8 ms 내외를 줄일 수 있다.
